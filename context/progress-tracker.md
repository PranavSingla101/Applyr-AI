## Decisions Made During Build

- 08a Extraction Not Persisting Fix (2026-07-07): reported bug — after "Extract from Resume," the auto-filled fields looked right in the form but vanished on reload. Root cause: `handleExtract` in `ProfilePageClient.tsx` only called `setValues`/`setSuggestions` (local React state) and never called `saveProfile()` — nothing was ever written to the DB, so extraction was purely cosmetic until the user separately clicked "Save Profile." Fixed by adding a `persistValues()` helper that calls the existing `saveProfile()` Server Action, and calling it immediately after the blank-fill merge in `handleExtract` and after `handleAcceptSuggestion` (accepting a conflict suggestion is also an extraction-driven change that would otherwise be lost the same way). Conflict fields the user already typed something into are untouched by this auto-save unless the user explicitly clicks the suggestion bubble to accept it — dismissing a suggestion doesn't touch `values` at all, so nothing to save there. Manual "Save Profile" still works unchanged for the user's own typed edits.
- 08 Resume PDF Generation from Profile (2026-07-07): added `app/api/resume/generate/route.ts` (loads the profile, gates on `full_name` + at least one work-experience entry with company+title, calls GPT-5.4 nano for a professional summary and 3-5 polished bullets per role from the raw `responsibilities` text, renders via new `lib/pdf/ResumeDocument.tsx` with `renderToBuffer`, uploads to storage, updates `profiles`) and `app/api/resume/generated/route.ts` (download route, mirrors `app/api/resume/route.ts`'s pattern). Two changes from the original `build-plan.md` text, both explicit developer decisions made during `/architect` planning before implementation: **(1) Model** — GPT-5.4 nano instead of GPT-4o, widening the existing "GPT-5.4 nano is only for resume extraction" exception (Feature 07) to also cover generation; uses `max_completion_tokens: 1000` for the same reason as extraction (`gpt-5.4-nano` rejects `max_tokens`). **(2) Storage path** — the generated PDF is written to `resumes/{user_id}/generated-resume.pdf`, a separate path from the user's uploaded resume (`resumes/{user_id}/resume.pdf`), rather than overwriting it as the original build-plan text specified. This required new `profiles.generated_resume_pdf_url`/`generated_resume_pdf_key` columns (migration `migrations/20260707135434_add-generated-resume-columns.sql`, applied) since the existing `resume_pdf_url`/`resume_pdf_key` must keep pointing at the user's uploaded file for Extract (Feature 07) to keep working from the original. `ResumeUpload.tsx` gained a "View Generated Resume" link (reuses "View Current Resume"'s classes, logged in `ui-registry.md`) plus loading/error state for the existing (previously unwired) `onGenerateResume` button. `context/architecture.md`, `context/build-plan.md`, `context/library-docs.md`, `context/project-overview.md` updated to reflect both changes. **Not verified live:** same headless-login limitation as Features 06/07 — typecheck, lint, and `next build` pass, but the actual generate → view-PDF → confirm-original-untouched flow needs manual browser verification.
- 07d Resume Extraction Conflict Suggestions (2026-07-07): extended Feature 07's blank-fields-only merge with a conflict-resolution UI for the case where the user already typed something *and* the resume disagrees — previously that case was silently ignored (the user's typed value always won, extraction data for that field was just dropped). New `diffExtractedProfile()` in `lib/profile.ts` finds scalar fields (`ScalarProfileField` — same 13 fields `mergeExtractedProfile` already treats as scalar; arrays and block fields like `workExperience`/`education` are excluded, same reasoning as the merge) where the current trimmed value and extracted trimmed value are both non-empty and differ. `ProfilePageClient.tsx` computes this diff right after the blank-fill merge and stores it as `suggestions` state (keyed by field). New `components/profile/SuggestionBubble.tsx` renders inline below the relevant input via a new optional `suggestion` slot on `ProfileForm.tsx`'s internal `Field` helper — clicking the bubble text applies the resume's value (`onAcceptSuggestion`, overwrites + recomputes completion), clicking the `X` dismisses it and keeps what the user typed (`onDismissSuggestion`), and manually editing a field with a pending suggestion auto-clears that suggestion (`handleChange` diffs the patch keys against `suggestions` on every keystroke) since it would otherwise reference a now-stale "current value". Enum-valued fields (`workAuthorization`, `experienceLevel`, `remotePreference`) render the human label in the bubble via small lookup maps in `ProfileForm.tsx`, not the raw stored enum string. Bubble styling uses `bg-accent-muted`/`text-accent` (the tokens `ui-tokens.md` already assigns to "missing skill" badges) rather than introducing an `info`/`warning` token for this — logged in `ui-registry.md`.
- 07c GPT-5.4 nano `max_tokens` Fix (2026-07-07): after the bundling fix, extraction reached OpenAI but failed with `400 Unsupported parameter: 'max_tokens' is not supported with this model. Use 'max_completion_tokens' instead.` — `gpt-5.4-nano` is on OpenAI's newer parameter surface (like the `o1`/reasoning-model family) and rejects the legacy `max_tokens` field entirely. Fixed in `app/api/resume/extract/route.ts` by switching to `max_completion_tokens: 800`. This is scoped to the `gpt-5.4-nano` call only — `gpt-4o` calls elsewhere in the app (matching, research synthesis, resume generation) keep `max_tokens` as documented. Recorded as an explicit rule in `library-docs.md` so it isn't silently "corrected" back to `max_tokens` later. `temperature: 0.3` was accepted without error, so left as-is; if a future request errors on `temperature` too, that's the next thing to check — OpenAI only reports the first invalid parameter per request, so a second unsupported-parameter error stacked behind this one was possible but did not materialize.
- 07b Resume Extraction Bundling Fix (2026-07-07): after the API key was filled in, extraction still failed every time with "Could not extract text from this PDF" — for a real uploaded resume, not a genuinely bad file. Reproduced by downloading the actual stored object (`npx @insforge/cli storage download`) and running the exact same `PDFParse({ data: buffer }).getText()` call in plain Node: it worked, extracting 3826 chars cleanly. The failure was specific to running inside Next's Turbopack-bundled route handler — `pdf-parse` v2 wraps `pdfjs-dist`, which resolves its worker/wasm assets in ways bundlers routinely break. Fix: added `serverExternalPackages: ["pdf-parse"]` to `next.config.ts` so it's excluded from the server bundle and runs as a plain Node `require`, matching the working standalone reproduction. Also added `console.error` logging in both catch blocks in `app/api/resume/extract/route.ts` (pdf-parse failure and GPT-5.4 nano failure) since the original silent swallow is exactly what made this take a manual repro to diagnose instead of just reading the dev server log. **Requires a dev server restart to take effect** — `next.config.ts` changes aren't hot-reloaded — which the agent cannot do per the "never restart the dev server" rule; the developer needs to restart it manually before retesting.
- 07 AI Profile Extraction from Resume (2026-07-07): added `app/api/resume/extract/route.ts` — auth check, looks up `resume_pdf_key` on `profiles` (404 if none), downloads the PDF from storage, extracts text with `pdf-parse` v2's `PDFParse` class (`new PDFParse({ data: buffer }).getText()` — v2 dropped the old `pdf(buffer)` default-export function entirely, docs in `library-docs.md` still show the v1 shape and need updating separately), rejects text under 50 chars with the standard "Could not extract text" error, then calls **GPT-5.4 nano** (not GPT-4o — deliberate exception scoped to resume extraction only, confirmed with the developer and documented in `library-docs.md`/`architecture.md`/`build-plan.md`) with `response_format: json_object`, `temperature: 0.3`, `max_tokens: 800` to return JSON matching `ProfileFormValues`. Client (`ProfilePageClient.tsx`) calls this route directly via `fetch()` (not a Server Action — extraction is agent-adjacent logic, so it stays behind an API route per the invariant that only API routes call into agent-style logic) from a new "Extract from Resume" button in `ResumeUpload.tsx`, shown once a resume exists server-side (`canExtract={Boolean(resumeUrl)}` — deliberately not gated on the local blob preview, since extraction reads from storage, not the in-memory file). Result is merged into form state via new `mergeExtractedProfile()` in `lib/profile.ts`: **merge, not overwrite** — scalar/array fields only fill if currently blank, `workExperience`/`education` are merged as whole blocks (not field-by-field) to avoid stitching a partially-filled role/degree together with mismatched extracted data. **Build-time gotcha:** originally instantiated the `OpenAI` client at module scope; `next build`'s page-data-collection phase evaluates route modules before some env resolution completes, and `OPENAI_API_KEY` is also currently empty in `.env.local` (developer needs to fill this in before extraction will work end-to-end) — moved instantiation inside the request handler so the build itself doesn't fail on a missing key at import time. Also added `resume_pdf_key` persistence retroactively via migration `migrations/20260707123443_add-resume-pdf-key.sql` (`saveResume()`/`saveProfile()` now save both `url` and `key`; `app/api/resume/route.ts` reads the key from the DB instead of hardcoding the storage path) — this was flagged as a gap in the Feature 06 log and fixed as a prerequisite for this feature, since extraction needs a reliable key to re-download the resume. **Not verified live:** same headless-login limitation as Feature 06 — typecheck, lint, and `next build` all pass; needs manual browser verification once `OPENAI_API_KEY` is set.

Verified via `pg_policy` that all 4 policies now exist on `storage.objects`.

## Notes

_Add notes here as the build progresses — workarounds, patterns, anything that differs from the context files._

- `@react-pdf/renderer` was listed in `code-standards.md`'s approved dependencies since Feature 05/06 planning but was never actually installed — `npm install @react-pdf/renderer` was required during Feature 08 before it could be imported. Its `renderToBuffer`/`Document` types require the element passed in to be typed as `ReactElement<DocumentProps>` specifically; a wrapper component (like `lib/pdf/ResumeDocument.tsx`) whose root JSX is `<Document>` still needs an explicit cast at the call site (`app/api/resume/generate/route.ts`) since TS doesn't structurally trace through a function component's return type.
- `@insforge/sdk`'s `storage.upload()` only accepts `(path, file: File | Blob)` — no third options argument, despite `library-docs.md`'s example showing `{ contentType, upsert }`. To upload a raw `Buffer` (e.g. a PDF rendered server-side, not a browser `File`), wrap it in `new Blob([new Uint8Array(buffer)], { type: "application/pdf" })` first.
